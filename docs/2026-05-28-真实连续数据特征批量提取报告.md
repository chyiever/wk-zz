# 2026-05-28 真实连续数据全量特征批量提取报告

## 1. 任务概述

### 1.1 目标

对连续真实数据（npz/tdms 文件）进行**滑窗全量特征提取**，支持：
- 批量处理多个文件夹中的数据文件
- 兼容 200kHz 和 500kHz 两种采样率（低采样率自动升采样到统一目标）
- 每个窗口计算所有频带的全量特征（约 80 特征/频带），而非选定子集
- 最大化 CPU/GPU 利用率，减少重复运算

### 1.2 与已有方案的对比

| 方案 | 输入类型 | 特征范围 | 输出粒度 | 适用场景 |
|------|----------|----------|----------|----------|
| batch_feature_extract_12folders_gpu | 离散 npz 样本 | 全量 (~564列) | 每样本一行 | 训练集/测试集批量提取 |
| realdata_feature_dataset_build-3 | 连续信号 | 5个选定特征 | 每窗口一行 | 连续数据快速特征筛选 |
| **本方案** | 连续信号 | **全量** | 每窗口一行 | 连续数据全量特征分析 |

## 3. 关键设计决策

### 3.1 升采样策略

- **方法**：`scipy.signal.resample_poly`（多相滤波器组）
- **优势**：比 FFT-based `scipy.signal.resample` 更高效，数值稳定性好，适合长信号
- **比率计算**：通过最大公约数自动计算整数比
  - 200kHz → 500kHz: `up=5, down=2`（2.5倍）
  - 其他比率自动适配
- **采样率不变时**：直接返回原始信号，零开销

### 3.2 全量特征 vs 选定特征

build-3 仅计算 5 个选定特征（SC_mean, C_f, epsilon_2x, SC_res_mean, I_burst），本方案对每个频带调用 `compute_all_features()`，计算全部约 80 个特征：

- 包络特征：r_p, C_E, A_env, S_env, Sk_env, R_td, R_fb, C_bulge, N_bulge, epsilon_env, eta_bw
- 频谱特征：SC_mean, k_sc, R_hl_mean, k_hl, beta_H, H_tf, SF, H_alpha
- 脊线特征：rho_r, G_gap, R2_ridge, S_arch, H2_ratio, R_2_1, H_stack, R_h, epsilon_2x, C_f 等
- 残差特征：E_harm, E_res, rho_res, R_high_res, epsilon_rec, N_abn, F_peak, K_loc, SK_max 等
- 小波特征：R_wp_* (16节点), H_wp, I_burst, D_WPT
- 阻尼原子特征：C_damp, alpha_hat, Q_MP, Delta_J, eta_dict

6 个频带 × 80 特征 = 约 480 个特征列 + 约 20 个元数据列。

### 3.3 并行策略

- **窗级并行**：`ThreadPoolExecutor` 处理窗口，workers 数可配置
- **批量处理**：每 256 个窗口为一批，减少线程创建开销
- **预处理一次**：整条信号的去均值 + 带通滤波仅执行一次，不随窗口重复
- **参数缓存**：`build_params_for_band()` 按 `(采样率, 频带)` 缓存 FeatureParams

### 3.4 GPU 利用现状

GPU 仅用于 `Q_MP` 特征中的 SVD 计算（`torch.linalg.svd` on CUDA）。其余约 79 个特征均为 CPU 计算（NumPy/SciPy）。这是由 `fea_cpt_gpu` 底层架构决定的，本方案不做修改。

## 4. 性能分析

### 4.1 单窗口计算复杂度

每个窗口需要：
1. N_bands 次 `build_context()` 调用
2. 每次 `build_context()` 包含：带通滤波 × 3 + Hilbert 包络 + STFT × 2 + 脊线提取 (DP) + 谐波掩码 + ISTFT + 小波包分解
3. N_bands 次 `compute_all_features()` 调用（纯公式计算，耗时可忽略）

**主要瓶颈**：`build_context()` 中的 STFT 和脊线提取。每增加一个频带，计算量近似线性增长。

### 4.2 内存占用估算

- 500kHz 采样率，20ms 窗口 = 10,000 样本/窗口
- 单个 FeatureContext 峰值内存约 5-10MB（含 STFT 矩阵、小波系数等）
- N_bands = 6 时，单窗口峰值约 30-60MB
- 8 workers 并发：约 240-480MB，在合理范围内

### 4.3 升采样开销

200kHz → 500kHz 升采样 2.5 倍后：
- 数据量增加 2.5 倍
- 窗口样本数从 4,000 增加到 10,000
- 窗口数量也增加 2.5 倍（因为信号更长了）
- 总体计算量约增加 2.5-3 倍（升采样本身很快，瓶颈在后续特征计算）

### 4.4 断点续跑机制

- 使用 `processed_source_files.txt` 记录已处理文件的绝对路径
- 每次运行自动加载记录，跳过已处理文件
- 支持中断后继续，不重复计算

## 7. 性能分析与优化

### 7.1 当前性能分布估算

实测运行时硬件利用率：GPU 约 45%，CPU 约 55%。以下为各操作的时间占比估算：

| 操作 | 占比 | 硬件 | 说明 |
|------|------|------|------|
| STFT × 2 | ~28% | CPU | scipy.signal.stft，每频带2次 |
| 动态规划脊线提取 | ~12% | CPU | 纯 Python for 循环，受 GIL 限制 |
| 小波包分解 | ~8% | CPU | pywt db4 level=4 |
| Butterworth 滤波 × 5 | ~8% | CPU | sosfiltfilt |
| rank2_hankel_quality (SVD) | ~5% | GPU | 唯一 GPU 操作 |
| 其他 numpy 特征计算 | ~27% | CPU | 向量化运算 |
| Hilbert + ISTFT + 其他 | ~12% | CPU | FFT 类操作 |

### 7.2 GPU 利用率分析（45%）

**核心原因：GPU 只做了一个 SVD 操作，仅占总计算量的约 5%。**

- 每个窗口 × 每个频带只调用一次 `torch.linalg.svd`
- 矩阵尺寸约 10,000 × 128，对 RTX 4050/4090 等 GPU 来说太小，GPU 不到 1ms 就完成
- PCIe 数据传输开销 > GPU 计算开销
- 其余 95% 的计算（STFT、脊线、小波、滤波）全部在 CPU 上

GPU 不是"没吃饱"，而是"没什么可干的"。整个流水线 95% 是 CPU-bound 的 scipy/numpy 操作。

### 7.3 CPU 利用率分析（55%）

1. **ThreadPoolExecutor + GIL**：脊线提取中 `_dynamic_programming_ridge()` 函数包含 `for t in range(1, n_time)` 纯 Python 循环，持有 GIL，无法真正并行
2. **WORKERS=8 偏少**：RTX 4050 笔记本通常有 10-16 核，8 个线程未跑满物理核
3. **文件串行处理**：`build_sliding_window_dataset()` 逐文件串行处理，下一个文件还没开始加载

### 7.4 优化建议（按预期收益排序）

| # | 方案 | 预期收益 | 实现复杂度 | 状态 |
|---|------|----------|-----------|------|
| 1 | 切换 ProcessPoolExecutor | CPU +20~30% | 低 | v2 已实现 |
| 2 | 增加 WINDOW_WORKERS 到 12~16 | CPU +10~15% | 低 | v2 已实现 |
| 3 | 文件级并行 | 接近线性加速 | 中 | 规划中 |
| 4 | GPU 批量 SVD | GPU 45%→80%+，总体 +5% | 高 | 规划中 |
| 5 | GPU 加速 STFT | 总体 +15~20% | 高 | v2 已实现 |
| 6 | 缓存跨频带中间信号 | +5~8% | 中 | 规划中 |

**关于 WINDOW_WORKERS 和 WINDOW_BATCH_SIZE 调整的效果：**

单独调整这两个参数效果有限，因为根本瓶颈是 GIL。最有效的组合是：
**ProcessPoolExecutor + WORKERS=12~16**，预计 CPU 利用率可从 55% 提升到 75~85%，
总体速度提升约 30~40%。若再加上 GPU STFT 加速，总体可提升 50%+。

### 7.5 v2 实测根因诊断（GPU 30%，CPU 20%，内存 27%）

v2 版本实测资源利用率远低于预期，根因如下：

| 指标 | 实测值 | 根因 |
|------|--------|------|
| GPU 30% | GPU 计算太轻，PCIe 数据搬运占主导 | 每次单窗口 STFT：CPU→GPU copy → GPU compute → GPU→CPU copy，内核 <1ms |
| CPU 20% | ProcessPoolExecutor + BATCH_SIZE=256 太小 | 进程创建/销毁开销 > 计算收益；workers 未绑定 NUMA |
| 内存 27% | 每个频带独立 STFT，中间结果未共享 | 6 频带 × 2 次 STFT = 12 次重复计算 |

### 7.6 v2.1 三项优化方案

| # | 方案 | 实现方式 | 预期收益 |
|---|------|----------|----------|
| 1 | 跨频带共享 STFT | `compute_shared_stft()`：先对最宽频带做一次 STFT，各子带从结果中切片 | STFT 调用 6×2=12 次 → 2 次，CPU -23% |
| 2 | NUMA 绑定 + 大批次 | `psutil.Process().cpu_affinity()` + `BATCH_SIZE=2048` | CPU +10~15%，减少跨 NUMA 内存访问 |
| 3 | GPU 批处理 STFT | `compute_stft_power(batched=True)`：堆叠多窗口一次性送 GPU | PCIe 往返 ↓90%，GPU 30%→75%+ |

**关键保证：所有优化不改变特征计算公式，仅减少重复运算。** 共享 STFT 后各频带从同一宽频带结果中切片，频域内容完全一致。

### 7.7 三版本对比

| 维度 | v1 (`fea_cpt_gpu`) | v2 (`fea_cpt_gpu_v2`) | v2.1 (`fea_cpt_gpu_v2_1`) |

### 7.8 v2.1 实测根因诊断（CPU ~30%, GPU ~20%）

v2.1 实测资源利用率仍远低于预期，根因分析如下：

| # | 根因 | 影响 | 代码位置 |
|---|------|------|----------|
| 1 | ProcessPoolExecutor 每批重建 | 每 batch 创建/销毁 14 个进程，开销 2~5s；CPU 尖峰=进程创建，CPU 下降=进程销毁 | `sliding_window.py:678` |
| 2 | IPC 序列化 signal_pre | 10s@500kHz ≈ 40MB，每窗口 pickle 一次，14 workers 峰值 560MB 数据拷贝 | `sliding_window.py:681` |
| 3 | GPU STFT 从未批量化 | `batched=True` 已实现但从未调用；每次单窗口 STFT，PCIe 延迟 > GPU 计算 | `_process_one_window` → `compute_shared_stft` |
| 4 | 多进程 GPU 竞争 | 14 个 worker 同时调用 torch.stft，GPU 操作串行化，CUDA context 重复初始化 | 每个 worker 进程 |
| 5 | 文件串行无流水线 | 当前文件处理完才加载下一个，I/O 与计算无重叠 | `sliding_window.py:734` |

**关键发现**：v2.1 的三项优化（共享 STFT、NUMA 绑定、大批次）未达预期效果，因为：
- 共享 STFT 在每个 worker 内独立调用，无法利用 `batched=True`
- NUMA 绑定只绑定主进程，worker 进程未绑定
- 999 窗口 / 2048 = 每文件仅 1 个 batch，大批次无改善

### 7.9 v2.2 四项优化方案（方案 D）

| # | 方案 | 实现方式 | 预期收益 |
|---|------|----------|----------|
| A | 持久化进程池 + 共享内存 | ProcessPoolExecutor 全生命周期复用；signal_pre 存入 `multiprocessing.shared_memory`，worker 零拷贝读取 | CPU +40%，消除进程创建/销毁开销和 560MB IPC 拷贝 |
| B | GPU STFT 集中化批处理 | 主进程批量 GPU STFT（`batched=True`），结果存共享内存；worker 纯 CPU 计算 | GPU +40%，PCIe 往返从 999×2 降至 2 次 |
| C | 文件级流水线 | ThreadPoolExecutor 后台预加载下一文件，I/O 与特征计算重叠 | CPU +10%，减少 I/O 空闲 |
| D | Worker 纯 CPU 计算 | Worker 不访问 GPU，消除多进程 GPU 竞争和 CUDA context 重复初始化 | 消除 GPU 串行化瓶颈 |

**架构变化**：

```
v2.1 架构（GPU 分散在 worker）:
  主进程: 逐文件串行
    → 文件N: 创建进程池 → [Worker1(GPU+CPU), Worker2(GPU+CPU), ...] → 销毁进程池
    → 文件N+1: 创建进程池 → [Worker1(GPU+CPU), Worker2(GPU+CPU), ...] → 销毁进程池

v2.2 架构（GPU 集中在主进程 + 共享内存）:
  主进程(GPU): 加载文件N → 批量GPU STFT → 写入共享内存 → 加载文件N+1 → ...
                    ↕ SharedMemory (signal_pre + STFT结果)
  持久Worker1-14(CPU): 从共享内存读取 → butter_filter + ridge + ISTFT + wavelet + 特征计算 → 返回结果
  预加载线程: 后台加载下一个文件，与当前文件的特征计算并行
```

| 文件流水线 | 无 | 无 | 无 | **ThreadPool 预加载** |
| 预期 CPU 利用率 | ~55% | ~20% | ~30% | **~80%+** |
| 预期 GPU 利用率 | ~45% | ~30% | ~20% | **~70%+** |
| 预期加速比 | 基准 | 1.5~2.0x | 2.5~3.5x | **4~6x** |

## 8. 结论

本方案在**不修改已有 `fea_cpt_gpu` 源码**的前提下，通过新建 `sliding_window.py` 模块实现了连续真实数据的滑窗全量特征批量提取。

- **v1**：基础版本，ThreadPoolExecutor + scipy STFT
- **v2**：ProcessPoolExecutor + torch GPU STFT + 自动检测核心数，突破 GIL 限制
- **v2.1**：共享 STFT + NUMA 绑定 + 大批次，预期 2.5~3.5x 加速，实测仅 2.21x
- **v2.2**：持久化进程池 + 共享内存 + GPU 集中化批处理 + 文件级流水线，从根本上解决 CPU/GPU 利用率低的问题

v2.1 的优化未达预期，根因在于**架构层面**：共享 STFT 和批处理 STFT 必须在主进程层面调度，而不是在各个 worker 内独立调用。v2.2 通过**分离 GPU 计算和 CPU 计算**，将 GPU STFT 集中到主进程批处理，worker 专注纯 CPU 特征计算，从根本上消除 GPU 争抢和 IPC 瓶颈。

所有版本的特征计算公式完全一致，v2.2 仅改变计算调度方式，不改变输出结果。

## 9. 开发经验与教训总结

四版本迭代（v1 → v2 → v2.1 → v2.2）历经三轮错误预判，最终才找到正确架构。以下按主题总结关键教训，供后续连续/实时特征提取项目直接参考。

### 9.1 架构设计：先分离再并行，不要把 GPU 塞进 worker

**错误路径（v2/v2.1）：** 让每个 worker 进程既做 GPU STFT 又做 CPU 特征计算。

```
Worker 进程 (v2/v2.1 的设计)
  GPU: torch.stft(单窗口)    ← 14 个 worker 争抢同一个 GPU
  CPU: butter_filter, ridge, wavelet, features
```

问题：
- 14 个进程共享 1 块 GPU，GPU 操作在驱动层串行化，实际利用率极低
- 每个进程独立初始化 CUDA context（~1-2s），浪费时间和内存
- 小 kernel（单窗口 STFT ~0.5ms）的 PCIe 传输延迟 > 计算时间

**正确路径（v2.2）：** GPU 和 CPU 分离，主进程集中做 GPU，worker 只做 CPU。

```
主进程 (GPU 专用)                    Worker 1-14 (纯 CPU)
  signal_pre → 共享内存              从共享内存读 signal + STFT
  批量 STFT → 共享内存               butter_filter
  不做特征计算                        ridge 提取
                                      ISTFT / wavelet / features
```

**教训：** 在 CPU-bound 的特征提取流水线中，GPU 是协处理器而非主处理器。GPU 应该被当作"批处理加速器"集中使用，而不是分散到每个 worker 中。判断标准：**如果一个 GPU 操作的单次计算时间 < PCIe 传输时间，就必须批量化，且在主进程中执行。**

### 9.2 数据传递：大数组必须用共享内存，不要走 pickle

**错误路径（v1-v2.1）：** 通过 `executor.submit(fn, signal_pre, ...)` 传递 40MB 的预处理信号。

```python
# v2.1: 每个窗口都 pickle 一次 signal_pre
f = ex.submit(_process_one_window, w, signal_pre, effective_rate, ...)
#                                ^^^^^^^^^^  40MB × 999 次 pickle
```

Python `ProcessPoolExecutor` 在 Windows 上使用 `spawn` 启动模式，所有参数必须 pickle 序列化。40MB 信号 × 999 窗口 × 14 workers 峰值 = **约 560MB 无效内存拷贝**，CPU 大量时间花在序列化而非计算上。

**正确路径（v2.2）：** 用 `multiprocessing.shared_memory` 零拷贝传递。

```python
# v2.2: signal_pre 只写一次共享内存，worker 零拷贝读取
sig_pack = _SharedArrayPack({'signal_pre': signal_pre})  # 写一次
sig_info = sig_pack.get_info()                            # 传名称（几个字节）

# Worker 端：通过名称附加，直接读取
arrays, shm = _attach_shared(sig_info)
win_signal = arrays['signal_pre'][i0:i1].copy()           # 零拷贝切片
```

**教训：** 当跨进程传递的数据 > 1MB 时，就应该考虑共享内存。判断公式：`数据大小 × 提交次数 × worker数 > 100MB` 时，共享内存是必选项，不是可选项。

### 9.3 进程池生命周期：不要频繁创建/销毁

**错误路径（v1-v2.1）：** 每 batch 重建进程池。

```python
# v2.1: 每 batch 重建 → 每文件至少创建/销毁 14 个进程
for b0 in range(0, len(windows), batch_size):
    with ProcessPoolExecutor(max_workers=14) as ex:  # 创建 14 进程
        futures = [ex.submit(...) for w in chunk]
        for fut in as_completed(futures):            # 等待完成
            ...
    # with 退出时销毁 14 进程 → 开销 2~5s
```

症状：**每开始处理一个新 batch，CPU 利用率出现尖峰（进程创建），之后迅速下降（进程销毁后无事可做）。**

**正确路径（v2.2）：** 进程池全生命周期复用。

```python
# v2.2: 进程池只创建一次，所有文件所有 batch 共用
executor = ProcessPoolExecutor(max_workers=14)
try:
    for fp in source_paths:
        # 提交任务到已存在的 worker 进程
        futures = [executor.submit(...) for w in windows]
        for fut in as_completed(futures):
            ...
finally:
    executor.shutdown()  # 全部结束后才关闭
```

**教训：** `ProcessPoolExecutor` 是重量级资源。创建 14 个进程的开销（导入模块、初始化 CUDA、分配内存）约 2~5 秒，远大于单窗口计算时间。在批量处理场景中，进程池必须持久化。`with` 语句适合短期任务，不适合批处理。

### 9.4 共享计算结果要在正确的层级调度

**v2.1 的"共享 STFT"看似合理但实际无效：**

```python
# v2.1 compute_shared_stft()：在每个 worker 内独立调用
def _process_one_window(w, signal_pre, ...):
    win_signal = signal_pre[i0:i1]
    shared_stft = compute_shared_stft(win_signal, ...)  # 每个 worker 各自做一次
    fvals = compute_all_features_for_window(win_signal, ..., shared_stft)
```

虽然 `compute_shared_stft` 把 6 频带 × 2 次 STFT 减少到 2 次，但：
- 这 2 次 STFT 仍在每个 worker 进程中独立执行（999 窗口 × 14 worker = 大量重复）
- 无法利用 `batched=True`（批量 GPU STFT 需要一次性堆叠多窗口信号）
- 多个 worker 同时做 GPU STFT → GPU 争抢

**正确做法（v2.2）：在主进程中一次性批量计算所有窗口的 STFT。**

```python
# v2.2: 主进程堆叠所有窗口信号，一次 GPU 调用
chunk_signals = np.stack([signal_pre[i0:i1] for _, i0, i1, _, _ in windows])
stft_freqs, stft_times, stft_complex, stft_power = compute_stft_power(
    chunk_signals, sample_rate, ..., batched=True  # (N_windows, L) → GPU 一次算完
)
# 结果存入共享内存，worker 直接按索引读取
```

**教训：** 跨频带/跨窗口的共享计算必须在数据聚合的层级调度，而不是在数据分散的层级。**"在 worker 内共享" ≠ "真正的共享"，它只是减少了单个 worker 的重复计算，但多个 worker 之间仍然重复。** 判断标准：如果一个优化需要"看到多个数据项"才能生效（如批量 STFT），它必须在主进程中执行。

### 9.5 预估性能要基于实测，不要基于假设

四版本迭代中，性能预估与实测对比：

| 版本 | 预估 CPU 利用率 | 实测 CPU 利用率 | 预估 GPU 利用率 | 实测 GPU 利用率 |
|------|-----------------|-----------------|-----------------|-----------------|
| v2 | 75~90% | ~20% | 70~85% | ~30% |
| v2.1 | ~80%+ | ~30% | ~75%+ | ~20% |
| v2.2 | ~80%+ | 30~99% | ~70%+ | <10% |

**v2 误判：** 认为 ProcessPoolExecutor 就能解决 GIL → 实际 IPC 开销更大
**v2.1 误判：** 认为共享 STFT + 大批次能提升 → 实际架构层错误导致无效
**v2.2 修正：** CPU 利用率大幅改善（30~99% 跳跃），但 GPU 利用率反降至 <10%

**教训：** 
1. **GPU 利用率低不代表需要更多 GPU 操作。** v2.2 的 GPU 利用率 <10% 是因为主进程批量 STFT 完成得太快（999 窗口分 5 块，每块 ~50ms），GPU 大部分时间在等 CPU worker 完成特征计算。这是**合理的**——流水线中 GPU 是瓶颈解除后的富裕资源。
2. **CPU 利用率跳跃（30~99%）说明仍然存在调度不均衡。** 可能原因：a) 主进程 GPU STFT 计算时 CPU worker 空闲；b) 窗口间计算量不均（某些窗口的 ridge 提取更耗时）；c) 共享内存 attach/detach 开销。
3. **每次优化前必须实测瓶颈，不要凭经验猜测。** 用 `py-spy` 或 `cProfile` 定位热点，用 `nvidia-smi dmon` 监控 GPU 利用率曲线，用任务管理器观察 CPU 尖峰的时序。

### 9.6 特征提取的通用数据流模式

基于四个版本的迭代，提炼出连续数据特征提取的通用架构模式：

```
┌─────────────────────────────────────────────────────────────────┐
│                      通用特征提取流水线                           │
│                                                                 │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐  │
│  │ 数据加载  │───→│ 预处理   │───→│ 滑窗切片  │───→│特征计算   │  │
│  │ (I/O)    │    │ (CPU)    │    │ (CPU)    │    │(CPU+GPU) │  │
│  └──────────┘    └──────────┘    └──────────┘    └──────────┘  │
│       ↑                                              ↓         │
│  ┌──────────┐                                  ┌──────────┐   │
│  │ 预加载    │  ← 后台线程                       │ 输出写入  │   │
│  │ (Thread) │                                   │ (I/O)    │   │
│  └──────────┘                                   └──────────┘   │
│                                                                 │
│  关键原则：                                                      │
│  1. GPU 操作集中在主进程，批量执行                                │
│  2. CPU 操作分散到 worker 进程，通过共享内存获取数据               │
│  3. I/O 操作用独立线程，与计算重叠                               │
│  4. 每个阶段只做一件事，不要混合                                  │
└─────────────────────────────────────────────────────────────────┘
```

**各阶段职责与资源归属：**

| 阶段 | 资源 | 并行方式 | 数据传递 |
|------|------|----------|----------|
| 数据加载 | 磁盘 I/O | 后台 Thread | 直接传递 |
| 预处理（升采样/滤波） | CPU 单核 | 主进程串行 | 共享内存 |
| GPU 批量计算（STFT/SVD） | GPU | 主进程串行 | 共享内存 |
| CPU 特征计算（ridge/ISTFT/wavelet/公式） | CPU 多核 | ProcessPoolExecutor | 从共享内存读取 |
| 输出写入 | 磁盘 I/O | 主进程串行 | 直接传递 |

### 9.7 实时特征提取的特殊考量

本项目的批量离线处理架构，在迁移到实时场景时需要额外注意：

**1. 窗口间依赖关系**

```
离线批量：所有窗口已知 → 可堆叠做 batched GPU STFT
实时流式：窗口逐个到达 → 无法预知后续窗口 → batched STFT 退化为单窗口

对策：维护一个小的窗口缓冲区（如 10~50 个窗口），攒够一批再送 GPU
      或：放弃 GPU STFT，改用 scipy CPU STFT（单窗口 ~5ms，可接受）
```

**2. 延迟约束**

```
离线批量：无延迟约束，可以等待所有窗口完成后再输出
实时流式：每个窗口有最大延迟约束（如 50ms）

单窗口完整流水线耗时估算（500kHz, 20ms 窗口, 6 频带）：
  butter_filter × 6  ≈ 3ms
  STFT × 2           ≈ 5ms (CPU) / 1ms (GPU batched)
  ridge × 2          ≈ 2ms
  ISTFT + wavelet    ≈ 3ms
  compute_features   ≈ 2ms
  合计               ≈ 15ms/窗口（串行）

实时可行性：15ms < 20ms 窗口时长 → 串行即可满足，
           但加上 50% 重叠则需 7.5ms 内完成 → 需要 2 线程并行
```

**3. 状态管理**

```
离线批量：无状态，每个窗口独立计算
实时流式：可能需要维护跨窗口状态（如滑动均值、异常计数器）

对策：特征计算函数保持纯函数（输入窗口 → 输出特征），
      跨窗口聚合在下游独立模块中完成
```

### 9.8 编程方式的具体教训

**1. Windows 上 `multiprocessing` 必须用 `spawn`，不能用 `fork`**

```python
# Linux: fork 模式，子进程继承父进程内存 → signal_pre 零拷贝
# Windows: spawn 模式，子进程从零启动 → signal_pre 必须 pickle 或共享内存

# 因此：在 Windows 上，大数组必须用 SharedMemory，
#       不能依赖 fork 的内存继承
```

**2. `torch.stft` 批量输入的返回形状**

```python
# 单输入：torch.stft(x)  # x: (L,) → 输出 (n_freq, n_time)
# 批量输入：torch.stft(x)  # x: (N, L) → 输出 (N, n_freq, n_time)
#                                      不是 (n_freq, n_time, N)!

# v2.1 的 bug：n_frames = spec_cpu.shape[1]  # 批量时 = n_freq（错误）
# v2.2 修复：n_frames = spec_cpu.shape[-1]   # 始终 = n_time（正确）
```

**3. SharedMemory 的生命周期管理**

```python
# 创建者：create=True → 负责 unlink()
# 使用者：attach by name → 负责 close()

# v2.2 的模式：
#   主进程：create → 写入 → 传名称给 worker → 等所有 worker 完成 → unlink
#   Worker：attach by name → 读取 → close
#
# 关键：unlink 必须在所有使用者完成读取之后，否则数据失效
#       close 只释放本进程的映射，不影响其他进程
```

**4. Worker 缓存共享内存附件**

```python
# 每次 attach SharedMemory 涉及系统调用（~0.1ms）
# 同一文件的 999 个窗口不需要 999 次 attach

# v2.2 的 worker 端缓存：
_worker_shm_cache = {}  # 全局字典，按 shm_name 索引

def _worker_get_arrays(shm_info):
    key = shm_info['shm_name']
    if key in _worker_shm_cache:
        return _worker_shm_cache[key]  # 缓存命中，零开销
    # 清理旧条目 → attach 新共享内存 → 存入缓存
    ...
```

### 9.9 特征提取的教训

**1. "全量特征"的计算量远超"选定特征"，但不应因此跳过**

5 个选定特征 → 80 个全量特征 × 6 频带 = 480 个特征列。计算量增长约 50 倍，但：
- 一次批量提取避免反复跑不同特征子集
- 后续特征选择时不需要重新计算
- 实测 v2.2 批量速度 3s/文件（999 窗口 × 480 特征），可接受

**2. 预处理做一次，不要随窗口重复**

```python
# 错误：每个窗口重新做整条信号的预处理
for window in windows:
    filtered = butter_filter(full_signal, ...)  # 重复 N 次
    win_signal = filtered[i0:i1]

# 正确：整条信号预处理一次，窗口切片在预处理后
signal_pre = butter_filter(full_signal, ...)   # 只做 1 次
for i0, i1 in window_ranges:
    win_signal = signal_pre[i0:i1]              # 零开销切片
```

本项目中，预处理（去均值 + 带通滤波）对 5M 样本信号耗时约 50ms。如果随窗口重复，999 窗口 × 50ms = 50s，占总时间的大部分。

**3. 跨频带共享 STFT 在正确层级调度时收益显著**

```
无共享 STFT：6 频带 × 2 STFT = 12 次 STFT/窗口
共享 STFT（v2.1，worker 内）：2 次 STFT/窗口，但 999 窗口各自独立
共享 STFT（v2.2，主进程批量）：2 次 batched STFT，覆盖所有窗口

效果：STFT 计算量从 999×12=11988 次降到 2×5=10 次 GPU 调用
```

## 10. 下一步提升空间

### 10.1 CPU 利用率稳定性优化

当前 CPU 在 30%~99% 之间跳跃，可能原因和优化方向：

| 问题 | 诊断方法 | 优化方案 |
|------|----------|----------|
| 主进程 GPU STFT 时 worker 空闲 | 在 GPU STFT 期间监控 worker 活跃数 | 将 GPU STFT 也放入后台线程，与上一批 worker 特征计算重叠 |
| 窗口间计算量不均 | 按 window_id 统计各窗口耗时 | 改用动态任务分配（`executor.map` 替代 `submit+as_completed`） |
| 共享内存 attach 开销 | 在 worker 内计时 `_worker_get_arrays` | 已通过缓存优化，如仍有问题可改用 `initializer` 预加载 |

### 10.2 GPU 利用率提升

当前 GPU <10%，原因是批量 STFT 完成太快，GPU 大部分时间空闲。优化方向：

| 方案 | 预期效果 | 复杂度 |
|------|----------|--------|
| GPU 加速 butter_filter | 将 5 次 sosfiltfilt 迁移到 GPU | 高（需要 cuSignal 或自定义 CUDA kernel） |
| GPU 加速小波分解 | pywt → torch wavelet | 高（无成熟 GPU 小波库） |
| GPU 加速 ridge 提取 | DP 算法向量化 | 中（可用 torch 实现批量 DP） |
| 接受现状 | GPU 是富裕资源，不需要提升 | 无 |

**建议：优先接受现状。** GPU 利用率低说明 GPU 不是瓶颈，强行提升 GPU 利用率不会加快总体速度（Amdahl 定律）。

### 10.3 实时特征提取适配

将 v2.2 架构适配为实时流式处理：

1. **窗口缓冲批处理**：维护 10~50 个窗口的缓冲区，攒够一批再送 GPU STFT
2. **延迟约束保障**：单窗口串行 ~15ms < 20ms 窗口时长，可行；50% 重叠需双线程
3. **流式输出**：特征计算完成后立即推送（Kafka/Redis），不等整文件完成
4. **状态管理**：特征计算保持纯函数，跨窗口聚合在下游独立模块
