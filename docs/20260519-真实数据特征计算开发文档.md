## 2. 三个版本的实现差异

### 2.1 v1：基线实现（稳定优先）

主要特征：

1. 按文件串行处理。
2. 每个窗口单独做预处理（`demean + butter_filter`），再进入特征计算。
3. 每个窗口每个 band 调用 `build_context`，并通过全量特征流水提取后再选 5 个目标特征。
4. 每处理完一个源文件 append 一次 CSV，支持断点续跑。

优点：

1. 实现直接、定义清晰、可追踪性好。

缺点：

1. 计算链路冗长（虽然只要 5 个特征，但实际执行了大量非目标特征中间步骤）。
2. 窗口级重复预处理导致额外开销。
3. 串行主流程使 CPU/GPU 都难以充分利用。

---

### 2.2 v2：定义不变前提下的工程优化

核心改动：

1. 只保留 5 个目标特征的专用计算函数，不再走全量特征导出列筛选模式。
2. 整条信号先预处理一次，再滑窗（避免窗口内重复预处理）。
3. 引入窗级并行（批处理窗口）。
4. 继续保留断点续跑和分片输出机制。

性能表现（实测日志）：

1. 单文件耗时由 v1 的约 `302s/文件` 降至约 `52s/文件`，提升约 5.8 倍。

注意点：

1. v2 与 v1 的数值会存在“接近但不完全一致”的差异，主要由预处理时序变化引起（整段预处理 vs 窗内预处理），不是特征定义本身变化。

## 3. 为什么会出现“版本间数值不一致”

### 3.1 不一致的第一来源：特征定义路径变化

`SC_mean` 在中途 v3 中曾从“基于 `build_context` 的 STFT 功率质心时序平均”改为“单窗 FFT 批量质心近似”，两者不是同一数学定义，导致系统性偏差。

### 3.2 不一致的第二来源：预处理时序变化

v1 与 v2 的预处理顺序不同：

1. v1：每窗预处理后提特征。
2. v2：整段预处理后再切窗提特征。

这会引入边界效应差异和局部频谱差异，因此会出现“值接近但不完全相同”的现象。

### 3.3 不一致的第三来源：并行与浮点路径

即使特征定义一致，多线程调度、FFT 后端、浮点累积顺序变化也会引入微小数值波动。这类差异通常应保持在可接受容差内。

## 4. 性能与资源利用观察

根据开发过程日志与反馈：

1. v1 约 `302s/文件`，CPU/GPU 利用率都偏低。
2. v2 约 `52s/文件`，速度显著改善，但 CPU 利用率约 `27%~30%`，GPU 利用率约 `4%~8%`。
3. v3（中途 GPU 改造）约 `46s/文件`，较 v2 仅小幅提升，且曾引入定义偏差风险。

说明：

1. 当前瓶颈主要不在“GPU 算子算力不足”，而在 Python 调度、窗级碎任务、I/O 与数据搬运开销。
2. “低 GPU 利用率”不必然代表实现错误，很多信号处理链条仍以 CPU 主导。

## 5. 高效率特征计算的经验与教训

### 5.1 经验：先做结构性减法，再做并行化

有效策略顺序应为：

1. 只算需要的特征。
2. 消除重复预处理。
3. 再引入并行与批处理。

该顺序在本次从 v1 到 v2 的提升中得到验证。

### 5.2 教训：性能优化不能改变特征数学定义

1. 同名特征如果换了实现定义，结果对不上是必然。
2. 优化版本必须先过“定义一致性验证”，再谈速度。

### 5.3 经验：建立“性能-一致性”双指标验收

建议固定两类验收：

1. 性能指标：`秒/文件`、`秒/窗口`、CPU/GPU 利用率。
2. 一致性指标：同一 `source_file_name + window_id` 下，关键特征 `MAE/P95/相对误差`。

未通过一致性阈值时，优化不可合入主流程。

### 5.4 教训：GPU 改造要有明确边界

1. 只把数学定义完全等价且批量化收益大的模块迁移到 GPU。
2. 复杂流程（如动态规划 ridge）若暂未批量 GPU 化，整体收益会被 CPU 部分限制。
3. 在“端到端未 GPU 化”前，追求高 GPU 利用率意义有限。

## 6. 建议的后续开发路线

### 6.1 短期（稳健优先）

1. 以当前“定义对齐版 v3（等价 v2）”作为可用基线。
2. 增加自动一致性回归脚本（对比 v2/v3 同窗口输出）。
3. 在不改变定义前提下尝试文件级并行（多进程）提升总体吞吐。

### 6.2 中期（性能优先）

1. 对每个特征建立“公式级单元测试”，再逐步替换为 GPU 批处理算子。
2. 按模块迁移（先 `SC_mean`，再 ridge 相关），每一步都做一致性对比。
3. 建立小样本基准集，任何优化先过基准再全量跑。

### 6.3 长期（工程化）

1. 将 notebook 逻辑沉淀为可复用 Python 模块（I/O、预处理、窗口化、特征核、写出器）。
2. notebook 仅保留参数和调度，降低后续维护成本。

---

## 7. 当前结论

1. v1、v2、v3 三版差异的根本原因已明确：定义路径与预处理时序变化。
2. “速度提升”与“定义一致”需要同时管理，不能只优化其一。
3. 当前可用策略是先锁定定义一致，再逐步做可验证的性能优化。
