# 2026-5-5 特征批量提取 CPU 和 GPU 开发文档

## 1. 文档目标

本文档用于总结当前仓库中两套批量特征提取方案（CPU 版与 GPU 版）的工程实现方式、数据处理逻辑、已识别瓶颈、已完成优化、风险点以及下一步可执行的提升路径。

文档覆盖的实现入口：

- `notebooks/batch_feature_extract_12folders.ipynb`（CPU）
- `notebooks/batch_feature_extract_12folders_gpu.ipynb`（GPU）

核心代码模块：

- `src/fea_cpt/*`
- `src/fea_cpt_gpu/*`

---

## 2. 总体方案概览

### 2.1 CPU 方案（直接优化现有程序）

方案目标：

- 保持原特征定义和计算口径不变。
- 在现有 `fea_cpt` 代码基础上做性能优化与稳定性修复。

当前实现特点：

- 每个样本按 7 个频带循环计算。
- 每个频带调用 `build_context -> compute_all_features`。
- 样本级并行由 notebook 中 `ThreadPoolExecutor / ProcessPoolExecutor` 控制。

### 2.2 GPU 方案（复制代码后独立优化）

方案目标：

- 保留与 CPU 版一致的特征定义与输出字段。
- 在 `src/fea_cpt_gpu` 中提供可选 GPU 加速路径，并支持自动回退 CPU。

当前实现特点：

- 结构完全复用 CPU 版流程。
- 新增 `src/fea_cpt_gpu/gpu_backend.py` 管理 GPU 可用性和 CUDA 计算。
- 当前 GPU 加速点集中在 `Q_MP` 对应的 Hankel 矩阵 SVD 计算。

---

## 3. 数据处理思路与编程实现逻辑

### 3.1 输入与标签组织

按文件夹批量提取，使用固定 12 个数据子集：

- 断丝类标签 `1`：`BK14_f130_*`, `BK14_f130a_*`, `BK14_f130c_*`
- 噪声类标签 `0`：`F130_*`, `F130A_*`, `F130C_*`

每个样本读取 `npz` 的 `phase_data`、`sample_rate`、`type` 等字段，生成 `FeatureRecord`。

### 3.2 样本内处理流程（两方案一致）

单样本特征提取主流程：

1. 预处理：去均值 + `1k~100k` 带通（`PREPROC_BAND`）。
2. 对每个频带构建参数：`build_params_for_band`。
3. 构建上下文：`build_context`。
4. 计算全特征：`compute_all_features`。
5. 按 `band__feature` 形式拼接特征列。
6. 添加元信息列：`label`, `sample_name`, `sample_rate`, `folder_name`。

### 3.3 输出组织

- 每个文件夹输出 1 个 CSV。
- 当前每个样本输出列规模约为：
  - `7 频带 * 80 特征 + 4 元信息 = 564 列`。

## 4. CPU 版实现细节与优化点

### 4.1 关键实现文件

- Notebook 调度：`notebooks/batch_feature_extract_12folders.ipynb`
- 特征计算：`src/fea_cpt/features.py`
- 信号上下文：`src/fea_cpt/signal_ops.py`

### 4.2 已完成优化

#### 优化 A：`_local_kurtosis_max` 向量化

原问题：

- 老实现为 Python 循环逐窗调用 `scipy.stats.kurtosis`。
- 在长样本、多频带场景下调用次数极高，成为主耗时瓶颈。

现实现：

- 使用 `numpy.lib.stride_tricks.sliding_window_view` + 批量 `kurtosis(axis=1)`。

效果：

- 在实测样本中该部分提速为数量级提升，显著降低单样本耗时。

#### 优化 B：参数缓存

- 在 notebook 内通过 `_PARAMS_CACHE` 按 `(sample_rate, band)` 缓存参数对象。
- 避免重复构建相同频带参数。

#### 优化 C：数值稳定性修复

- 修复 `eta_bw` 在边界样本分母为 0 的问题。
- 改为 `max(1, eta_den)` 保护，避免 `ZeroDivisionError`。

### 4.3 当前 CPU 版瓶颈

尽管已优化，CPU 版仍存在以下结构性成本：

- 每个样本对 7 个频带重复构建完整上下文（包含滤波、STFT、ridge、wavelet 等）。
- `compute_all_features` 中仍有大量中小矩阵运算，累计 CPU 代价高。
- notebook 调度层仍以样本级 future 管理，任务粒度大时早期进度更新不均匀。

## 5. GPU 版实现细节与优化点

### 5.1 关键实现文件

- Notebook 调度：`notebooks/batch_feature_extract_12folders_gpu.ipynb`
- GPU 后端：`src/fea_cpt_gpu/gpu_backend.py`
- GPU 特征：`src/fea_cpt_gpu/features.py`

### 5.2 当前 GPU 编程实现方式

#### 5.2.1 GPU 启停策略

- 环境变量 `FEA_CPT_USE_GPU` 控制启用。
- `gpu_backend_info()` 输出设备状态。
- 当 `torch` 不可用或无 CUDA 时自动回退 CPU。

#### 5.2.2 已接入 GPU 的计算点

- `Q_MP` 对应 rank-2 Hankel 重构质量中，SVD 优先走 `torch.linalg.svd`（CUDA），失败则回退 NumPy。

#### 5.2.3 并行策略

- GPU notebook 中默认使用线程池。
- 当检测到 GPU 启用时，强制线程池，避免 `ProcessPool + CUDA` 组合导致的进程异常。

### 5.3 GPU 版当前收益与限制

收益：

- 在 `Q_MP` 特征上可获得 CUDA 加速。
- CPU 回退链路完整，部署容错性较好。

限制：

- 目前只有局部算子（SVD）GPU 化，不是全链路 GPU。
- 数据仍在 NumPy/CPU 与 torch/GPU 间发生转换，存在拷贝开销。
- 对于短样本和轻量矩阵，GPU kernel 启动与数据传输开销可能抵消收益。

## 6. 现有瓶颈分析（CPU/GPU 共性）

### 6.1 计算图重复

当前是“频带循环驱动上下文重算”模式，同一样本跨频带存在重复计算空间。

### 6.2 IO 与内存占用

- 大规模样本（如 2000+）批量运行时，长期任务对内存、文件系统写入和 DataFrame 拼接均有压力。

### 6.3 notebook 承载过多业务逻辑

- 目前 notebook 内含完整调度和核心函数，复用性和可测试性较弱。

### 6.4 文档与 notebook 文本编码风险

- 当前仓库部分历史文档和 notebook markdown 出现乱码，后续维护成本上升。

---

## 7. 下一步提升空间（建议路线）

### 7.1 P0：稳定性与工程化（优先）

1. 将 notebook 中函数区下沉为 `src/fea_cpt/pipeline_batch.py` 与 `src/fea_cpt_gpu/pipeline_batch.py`。
2. 增加异常样本日志（文件名、频带、异常类型），支持“跳过坏样本继续跑”。
3. 增加分块写出（例如每 500/1000 样本落盘）避免长任务失败全损。

### 7.2 P1：CPU 性能继续提升

1. 评估“样本级全频缓存 + 频带掩膜派生”的重构方案，减少频带间重复 STFT/滤波。
2. 为高频调用函数增加向量化和避免重复分配。
3. 在纯 CPU 模式下评估 `ProcessPoolExecutor`（禁 GPU）与线程数上限自动寻优。

### 7.3 P1：GPU 链路扩展

1. 将 STFT/谱矩阵统计迁移到 torch/cupy（先做批量张量化）。
2. 将频带掩膜、能量比、谱心等批量特征改为 GPU 并行张量计算。
3. 建立 CPU/GPU 一致性回归测试（rtol/atol 阈值）。

### 7.4 P2：数据与结果管理

1. 从 CSV 迁移为 `parquet + metadata`，提高写入和读取效率。
2. 建立特征版本号（参数、代码 hash、数据源）以支持可追溯对比。

## 8. 运行建议（当前版本）

### 8.1 CPU 版

- 使用 `notebooks/batch_feature_extract_12folders.ipynb`。
- 默认 `PARALLEL_BACKEND='thread'` 运行稳定。
- 若切换到 `process`，建议在非 GPU 环境下使用。

### 8.2 GPU 版

- 使用 `notebooks/batch_feature_extract_12folders_gpu.ipynb`。
- 使用 `py312` + CUDA 环境。
- 保持线程池并行，避免 `BrokenProcessPool` 风险。

## 9. 已知问题与处理结论

### 9.1 已解决

1. `eta_bw` 除零异常（CPU/GPU 已修复）。
2. GPU 版 `ProcessPool` 导致的池崩溃风险（默认线程化规避）。
3. notebook 配置段乱码（已替换为可读文本版本）。

### 9.2 待继续观察

1. GPU 版整体吞吐是否随样本规模稳定提升（当前仅局部 GPU 化）。
2. 不同采样率混合数据（200k/500k）下的跨设备性能差异。

---

## 10. 结论

当前两套方案已经具备可运行、可导出、可扩展的基础能力：

- CPU 版已经通过关键热点优化获得显著提速，并修复数值稳定性问题。
- GPU 版完成了独立目录实现与安全回退机制，具备逐步扩展 GPU 算子覆盖率的工程基础。

后续最优推进策略不是一次性“全 GPU 重写”，而是按计算热点分阶段迁移，并以一致性回归和批量压测作为上线标准。

## 11. 执行附录（任务清单化）

本附录用于将后续优化工作拆解为可执行任务。每个任务包含目标、实施动作、验收标准与交付物，便于排期和分工。

### 11.1 P0（稳定性与工程化，优先完成）

1. 任务编号：P0-01  
目标：将 notebook 内核心流程下沉为可复用模块。  
实施动作：新增 `src/fea_cpt/pipeline_batch.py` 与 `src/fea_cpt_gpu/pipeline_batch.py`，封装批量入口、并行策略、异常处理。  
验收标准：notebook 只保留参数配置与调用入口，核心逻辑迁移完成且结果一致。  
交付物：2 个 pipeline 文件、2 个精简后的 notebook。

2. 任务编号：P0-02  
目标：实现坏样本可跳过并持续运行。  
实施动作：在单样本处理处统一 try/except，记录 `sample_name`、`folder_name`、`band`、`error_type`、`traceback`。  
验收标准：存在异常样本时批处理不中断；最终输出错误日志文件。  
交付物：`failed_samples.csv`、异常日志写入代码。

3. 任务编号：P0-03  
目标：降低长任务失败损失。  
实施动作：增加分块落盘机制（例如每 500 或 1000 样本写一次 parquet/csv），支持断点续跑。  
验收标准：任务中断后可从最近 checkpoint 继续，不重复已完成样本。  
交付物：checkpoint 文件规范、续跑控制参数。

4. 任务编号：P0-04  
目标：建立基础一致性回归。  
实施动作：固定样本集（含 200kHz 与 500kHz），对 CPU 与 GPU 回退路径输出做逐特征对比。  
验收标准：所有特征满足阈值 `rtol=1e-5, atol=1e-7`；自动输出差异报告。  
交付物：`tests/test_feature_consistency.py`、对比报告模板。

### 11.2 P1（性能优化，第二优先级）

1. 任务编号：P1-01  
目标：减少跨频带重复计算。  
实施动作：设计并实现“样本级缓存上下文”，将可复用谱量与时频中间量缓存后按 band 派生。  
验收标准：单样本总耗时较当前版本下降至少 20%。  
交付物：缓存上下文类、性能对比记录。

2. 任务编号：P1-02  
目标：扩展 GPU 覆盖范围。  
实施动作：将 STFT、谱统计、频带掩膜、能量比等批量张量运算迁移到 torch/cupy。  
验收标准：在 GPU 环境下 1000 样本批处理吞吐提升明显，且一致性测试通过。  
交付物：GPU 算子实现、GPU profiler 结果。

3. 任务编号：P1-03  
目标：优化并行策略。  
实施动作：建立自动并发推荐逻辑，按 CPU-only / GPU 模式分别选择线程数和后端。  
验收标准：默认配置在主流机器上稳定运行，无 `BrokenProcessPool`，吞吐不低于手工调参。  
交付物：并行策略函数、参数建议文档。

4. 任务编号：P1-04

实施动作：将逐样本 dict 累积改为分块 DataFrame 或 Arrow 表写入，减少大对象常驻。  
验收标准：大数据集运行时峰值内存下降，可量化对比。
